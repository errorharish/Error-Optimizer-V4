# Pure rule modules (src/lib/eo)
Each module is pure (no React, no storage) and has a test in `src/test/`. UI reads the rules; it never re-implements them.
- `slider.ts`, `score.ts` — slider values and illustrative optimization score (`premium-rules.test.ts`). Why: every slider/score behaves the same.
- `autoOptimize.ts` — tasks, interval validation, run planning, overlap, summaries (`auto-optimize-rules.test.ts`). Why: one set of maintenance safety rules.
- `quickActions.ts` — two Dashboard groups: `NAV_SHORTCUTS` (kind "navigate", only open a page) and `QUICK_OPTIMIZE` (kind "run", own steps in place, one run at a time) (`quick-actions.test.ts`). Why: user-directed — navigation and optimization never mix.
- `restorePoint.ts` — System Protection / restore-point state machine (`restore-point-rules.test.ts`). Every create-restore-point path uses `useRestorePointFlow` / `RestorePointDialog` from `src/components/eo/RestorePoint.tsx`; simulated device state is in `restorePointStore.ts`. Why: protection is checked, confirmed and verified the same way everywhere.
- `health.ts` — System Health scoring, rendered only by `HealthCheck.tsx` (`health-score.test.ts`); the check is manual-only and never restores a past result. Why: one documented, reproducible method.
- `dashboardScan.ts` — dashboard scan readings → Overall Optimization Score and V4 readiness (`dashboard-scan.test.tsx`); only the V3 and V4 dashboards auto-scan via `src/components/eo/useSystemScan.ts` (WebView2 `system:scan`, labelled sample fallback). Why: scores come from readings, never hardcoded, and only dashboards scan on open.
- `registryValues.ts` — RAM and GPU registry values transcribed from the WPF `MachineRegistryValueEngine` / `GpuRegistryValueEngine`, with hardware/profile applicability gates (`registry-values.test.ts`). Why: the Registry Values overview shows only values the native engines support.
- `inputModes.ts` — Normal/Advanced selections are computed from the shared default rule; Custom is a saved `usePersistedSelection` profile edited through a draft (`input-modes.test.ts`). Why: recommendation-driven modes never drift from the rule.
- `theme.ts` — normal colour presets + saved custom themes (colours only, no effect identity; removed or unknown ids sanitize to ERROR DEFAULT), hex validation + `validateThemeDraft`, draft (live) → Save / Discard / Restore previous state and the `--theme-*` variables (`theme-rules.test.ts`); applied app-wide only by `src/components/eo/themeStore.ts` (pre-paint script in `__root.tsx`), edited only in `ThemeSettings.tsx`. Every colour token in styles.css derives from `--theme-*`; pages never hardcode hues, and there is no decorative VFX layer (premium look comes from static gradients, borders, shadows and functional motion). Why: one theme recolours V3 and V4 together and stays clean and stable.
- `fileFilters.ts` — Storage file explorer drive/size/type/search/sort rules (`file-filters.test.ts`). Why: filters stay testable.
- `ramLimiter.ts` — per-application RAM targets for AUTO/LIGHT/AGGRESSIVE/MANUAL, eligibility (focus, critical, excluded) and reclaim/standby summary (`ram-limiter-rules.test.ts`); persisted UI state in `src/components/eo/ramLimiterStore.ts`. Why: every RAM Limiter panel shows one consistent configuration; enforcement stays in a future native bridge.
- `workload/` — Workload Optimization engine: discovery adapter, event-driven process monitor reducer, category rules, conflict manager (non-overlapping affinity, only the focused app gets High), custom-app CRUD (`workload-rules.test.ts`); UI store `src/components/eo/workloadStore.ts`. `backend.ts` talks to the .NET host over WebView2 messages (`workload:*`) and falls back to a labelled simulator. Why: one shared workload state feeds the running list and summary tiles; native actions are never faked as real.
- `ramTargets.ts` — RAM Limiter Configured Targets: only apps the user adds are passed to `summarize`/enforcement via `configuredApps`; every add/restore path goes through `checkTargetEligibility` (normalized exe + PID, never display name: critical, policy-protected, in focus, shielded) inside `addTarget`, called only via `addConfiguredTarget`/`addCustomTarget` in `ramMonitorStore.ts` against the engine's live process list; `setRamState` re-sanitizes targets and the engine re-checks each PID right before apply. Temporary blocks keep the target; policy-protected ones are dropped (`ram-eligibility.test.ts`). Why: no path can add or limit a focused, shielded or protected app.
- RAM Limiter always-on engine: `planEnforcement` / `reduceRamEvent` in `ramLimiter.ts` diff applied vs required targets on every process/config event (no timer); `ramLimiterBackend.ts` talks to the host over WebView2 `ram:*` messages with a labelled simulator; wired in `src/components/eo/ramMonitorStore.ts`. Why: targets are applied once per change, never re-trimmed on a schedule.
- `v4Telemetry.ts` — CPU/GPU/RAM usage shown inside the V4 Readiness card (background count is computed but not displayed): live WebView2 `telemetry` samples via `src/components/eo/useLiveTelemetry.ts` (`telemetry:subscribe` / `unsubscribe`), else the native scan; sample readings are never shown, missing values are "--" (`v4-system-performance.test.ts`); when no real reading exists the panel shows labelled demo values from `simulatedUsage.ts` (`simulated-usage.test.ts`), dropped as soon as real data arrives. Why: real Windows telemetry only, shown once on the V4 Dashboard with no standalone performance card.
- `headingCase.ts` — page, section, modal and card headings render through kit components (`PageHeader`, `SectionTitle`, `Modal`, `Label as="h2|h3"`) which title-case all-caps titles and use the shared `.eo-heading` / `.eo-card-heading` styles (`heading-case.test.ts`). Why: headings never set their own font size, weight or casing.
- `serviceHealth.ts` — global header SERVICE STATUS states (one `GlobalServiceStatus` in the Shell header on every V3 + V4 route) (connecting / online / offline) as a reducer plus ASP.NET Core health-response parsing (`service-health.test.tsx`); sources live in `serviceHealthBackend.ts` (HTTP `VITE_EO_SERVICE_HEALTH_URL`, else WebView2 `service:health`, else a labelled simulator) and polling in `src/components/eo/ServiceStatus.tsx`. Why: the badge never shows ONLINE without a real successful response, and the .NET backend plugs in without UI changes.
- `emulatorConnection.ts` — MSI App Player / ADB / guest connection states with dependency rules (ADB CONNECTED needs MSI RUNNING; guest READY needs ADB CONNECTED + an ADB-reported version), Review & Apply prerequisites and polling intervals (`emulator-connection.test.ts`); live state + WebView2 `emulator:*` protocol in `src/components/eo/emulatorConnectionStore.ts`, rendered only by `EmulatorDetectionBar` in `src/components/eo/emulatorUi.tsx` (shared section card, mode selector, selection item, action button and bottom bar for all three emulator pages) on all three V4 emulator pages (v4Store `adb` mirrors detected ADB); browser preview shows NATIVE SERVICE UNAVAILABLE and never a fake connection. Why: a running emulator process never implies ADB or guest readiness, and the Windows backend plugs in without UI changes.
- `settings.ts` — Control Center categories, saved preferences (startup, AI policies, performance, safety, logs, motion), safety confirmation rule and settings search (`settings-rules.test.ts`); stored by `src/components/eo/settingsStore.ts`. Why: settings persist and search opens the right category.
- `smartSearch.ts` — Smart Search ranking over the page registry (title > hosted modules > keywords > category > description; every typed word must match; shared pages rank last), suite grouping, recents and highlighting (`smart-search.test.ts`). Why: one search ruleset; results are always real routes.
- `pageScan.ts` — optimization page scan store: auto-scan on entry only without a result, session cache, one scan at a time, REFRESH forces a repeat, abandoned scans ignored (`page-scan.test.tsx`); used only via `src/components/eo/usePageScan.ts` and `PageHeader scan`. Separate from the dashboard score scan. Why: every optimization page scans and refreshes the same way.
- `thermals.ts` — Dashboard Temperature Monitoring: host thermal fields on the existing `telemetry` message (`cpu.tempC`, `gpu.tempC`, `gpu.hotspotC`, `ssd.tempC`), native-scan fallback (sample scans ignored), NORMAL/WARM/CRITICAL limits, sensor count, bounded 5-minute history with 30 SEC / 1 MIN / 5 MIN windows (buckets aligned to the sample count) and graph paths (`thermal-rules.test.ts`); fed only by `src/components/eo/useThermals.ts`, rendered only by `TemperatureCard.tsx`; browser values come from `simulatedThermals.ts` and are labelled SIMULATED DATA. Why: unreported sensors show SENSOR UNAVAILABLE and generated values never pass as hardware readings.
- `executionResult.ts` — operation-level run results (verified / failed / skipped / unverified) and the overall SUCCESS / PARTIAL / FAILED / UNVERIFIED / SKIPPED rollup, retry merge and the proposed `optimize:result` host parser (`execution-result.test.tsx`); shown only by `ExecutionResultPanel` / the root-mounted `ExecutionResultDialog` (`src/components/eo/ExecutionResult.tsx`, store `executionResultStore.ts`). Browser-preview runs report every operation SKIPPED via `simulatedResult` and never offer rollback. Why: a run is never called successful unless every operation was applied and verified.
